# Working in this directory

You are authoring **Microteia extensions**. Read this before writing or changing anything here.

> Generated by Microteia — rewritten whole every time this installation takes a new platform version.
> Do not edit it; anything you want to keep goes in `CLAUDE.md`, which is yours. (The config files are
> different: `sync` only adds what is missing there, so your own settings survive.)

## The one rule that explains all the others

An extension is a **declaration**, not a patch. You never modify the platform; you declare what you
want, and the platform installs it. Everything below follows from that.

## A screen is not an entity model: a screen shows fields, an entity owns them.

Before any of it: **model the domain, then generate.** A request arrives describing what someone will
SEE — "a sales screen with the customer, the salesperson and the products" — and the fastest reading
turns that sentence into one entity holding everybody else's data:

    Sale { customerName, customerEmail, sellerName, productName, quantity, ... }

That package validates. It installs. It runs. Nothing else in this platform will ever refuse it, and
that is exactly why this step exists. What it costs is paid later and paid forever: the customer's
name is now stored in every sale and drifts the day they correct it; there is no list of customers to
search, and no way to know which sales are theirs; three product slots means there is never a fourth;
and no total can be computed, because there are no line records to add up.

The same sentence, modelled: **Customer**, **Employee**, **Product**, **Sale**, **SaleItem** — with
Sale pointing at Customer and Employee, and SaleItem hanging from Sale and pointing at Product. The
screen you were asked for is then something the platform draws from that model, which is the right
order: a screen is a view of entities, never the shape of them.

So the sequence, and it is not optional:

0. **Write the rule down first**, as `{ id, statement, actors, concepts, invariants, processes,
   acceptance }`, with `statement` in the words it arrived in. The `model_business_rule` prompt
   conducts this and everything below. It is not paperwork: every "cannot", "must" and "only" in the
   sentence is an invariant, and `acceptance` is the only part that says whether the work landed —
   without it, "done" is an opinion. If the sentence does not answer one of them, ASK. A question now
   costs one message; the wrong entity costs every record written into it.
1. **Read `microteia://entities`** — what already exists here. A field called `customerName` is a
   defect *because* Customer is a thing, and this is how you learn that it is. Every entity says where
   it came from: `kernel`, `workspace` (a `plugin.ts` here, which you can edit) or `installation`
   (a snapshot of what the organization runs, which you cannot). Read `catalogSources` in the answer
   before trusting the list — if there is no snapshot, a screen somebody built in the Form Design and an
   extension already installed there are both invisible, and asking beats assuming. An administrator of
   the organization brings them in with **Export catalog** on the Extensions screen of the application;
   whoever administers the Firebase project can also run `microteia export-catalog --tenant <tenantId>`.
   Either one writes `installed-catalog.json` here, and the answer then says when it was taken.
2. **Write the domain model** — entities, what each field MEANS, and the relationships. The shape is
   `microteia://domain-model/schema`; every rule is `microteia://domain-model/rules`.
3. **`validate_domain_model`** — a deterministic engine, not an opinion. It catches a field that
   belongs to another entity, a group of fields reproducing one, a collection modelled as `item1,
   item2, item3`, a many-to-many with attributes stored as an array of ids, and a copy declared as a
   snapshot with no reason given.
4. **`generate_artifact_plan`** — a model with an ERROR does not become a plan. What comes back is
   what must exist, with each relationship already resolved to `refEntity` / `parentEntity` /
   `parentFieldKey`. Read it from there rather than re-reading the model: two readings of the same
   sentence is how they start to disagree. It also decides the SCREEN, by rule: which fields go to the
   list, which filter, which sections, which fields are read-only, and one record action per
   user-action transition with the `disabledWhen` the blocking invariant produced — its flow declares
   `recordId` (the record the button always sends) and ends in the `map` that answers the button,
   on every path. Pass the `rule`
   from step 0 and the plan becomes that rule's batch — a diff of what the rule generated last time.
   What the plan does not decide it hands back, named: the icon, the menu order, and where an
   ambiguous action appears. Do not fill those in silently.
5. **Write the `plugin.ts`, then `validate_plugin`.** The plan says what must exist; that one says
   whether what you wrote installs.
6. **Save the model as `<folder>/domain-model.json`.** This is the step people skip, and it is the one
   that stops the same argument happening every session. `source` and `reason` have nowhere to live in
   an installed field — a snapshot ships as a plain text column — so without the file, tomorrow's
   session reads the catalog, sees `productName` sitting on an invoice line, and raises it again. And
   again. Keeping it there is what makes a declared exception cost one decision instead of one per
   session; the checks read it back on their own.
7. **Save the rule and what it produced as `<folder>/business-rules.json`** — the plan hands it to you
   ready to write, under `trace.contents`. Without it, the NEXT version of that rule proposes a second
   batch of screens that look like the first, and "this replaces that" is left to whoever remembers.
   And when the rule loses an entity, the plan proposes DISABLING what it created — never deleting,
   because deleting a screen means deciding what happens to the records in it, and nothing here sees
   the records.

**The plan is a diff, not a creation.** It reconciles with what is already there, and it says what it
cannot do instead of working around it: a field's key and type are immutable once records exist, a
change to the shape of stored data needs a declared `migration`, and nothing is ever removed —
deleting a screen that holds records is a decision for a person looking at those records.

**Duplication is allowed; silent duplication is not.** The rule was never "never duplicate data". It
is: data that is a source of truth stays normalized *unless there is an explicit semantic reason* to
materialise or snapshot it. A line item's unit price is a correct snapshot — the price charged that
day must not change when the catalogue does. Say so:

    { key: 'unitPrice', semanticType: 'snapshot', source: 'Product.price',
      reason: 'the price charged on the day; a later catalogue change must not rewrite past sales' }

Undeclared, that same field is indistinguishable from an accident, and in six months nobody can tell
which one it was.

## Reach for the least powerful thing that works

Each rung costs strictly more than the one above it, and the cost is permanent — not a matter of taste:

| Rung | What it costs you, forever |
|---|---|
| A **screen** — its fields, rules and expressions | nothing. The platform draws the list, the detail, the form, the filters and the search |
| A **Widget DSL** page, tab or widget | nothing. No review, nothing to break, survives platform upgrades untouched |
| A **workflow**, **action** or **script** | runs in the platform's engine and sandbox: no review, but logic you now have to keep right |
| A **view** or **startup** — real React | an administrator must read and trust the source, again on every change, and you own that code across upgrades |
| A **Cloud Function** | the extension stays inert until someone provisions the organization's Firebase project |

Most of what looks like it needs React needs a declaration. A field that computes itself, a button
that hides for the wrong person, a badge counting what this person has not read, a value aggregated
from child records — all of those are declared, and `AUTHORING.md` says how. Reaching for a view
because it is the shape you know best is the single most expensive habit in this directory.

## When the platform is missing something — ask before working around it

Sooner or later you will need something the platform does not offer, and there will always be a way to
fake it: a hidden field that mirrors state, a workflow that writes what an expression cannot read, a
value recomputed on every save because nothing exposes it. Those tricks work. Each one is also a
capability the platform was missing, buried somewhere nobody will ever find it again.

Before writing one, decide which of the two gaps you are looking at:

| The gap | What to do |
|---|---|
| Specific to this extension, this organization or this screen | Work around it and move on. Nothing anticipates everything, and not every absence is a defect |
| **Agnostic** — it can be named without naming this business — and another extension would plausibly need it for the same reason | **Stop and ask.** Write nothing until the person you are working for has decided |

The test for the second row is the one the platform applies to itself: could the missing thing be named
without naming this business? *Whether the record is being created or is being edited* is agnostic —
every extension with a form reaches for it sooner or later, and a field expression that cannot see it
has to be tricked. *Whether the client has signed the contract* is not: that one belongs to the
extension, and working around it is the correct answer.

When it is the second kind, say so **before** you write anything, and say four things:

1. **What is missing** — the capability, named the way the platform would name it, not the symptom you
   hit.
2. **How the platform could supply it** — where the declaration would live and what it would look like
   to whoever writes an extension.
3. **Why it matters** — who else runs into this, and what they are forced to do today without it.
4. **What the workaround costs** — what you would write instead, and what has to be undone when the
   platform later grows the real thing.

Then wait. Being told to work around it is a legitimate answer and may well be the right one today —
but it is their decision, not yours. The one outcome that must not happen is the workaround going in
silently: the platform never learns what it is missing, and the next extension pays for it again.

## The gate — non-negotiable

Nothing is finished until all three of these pass:

    npx tsc --noEmit
    npx microteia-plugin check <folder>/plugin.ts
    npm test

`check` runs the *exact* validation the platform runs on install. If it passes, the package installs;
if it fails, the package would be refused. Do not hand over work that has not passed it.

**A failing test means the task is not done.** Never report work as finished — not as "done except
for", not as "done, one test still red" — while any of the three commands above fails. Either the code
is wrong and you fix it, or the test is wrong and you say so and fix *it*; a red test is never
something to hand over and explain.

**One exception: an error inside `examples/` is not yours.** `tsc` and `npm test` cover the whole
directory, examples included, and that is on purpose — it is what lets your editor resolve them. But
those files are ours, shipped with kernel contract 2.106.0, and replaced on the next `sync`:

- Do not edit them, and do not bend your own code to make their error go away.
- Do not count them against the gate. The gate is: no error and no failing test **outside**
  `examples/`.
- Do tell the person you are working for: the file, the error and kernel contract 2.106.0. It is
  a defect in the installed package, and that report is how it reaches whoever can fix it.

## Creating one

    npm run create              # guided; asks what the extension should carry
    npm run create:function     # adds a Cloud Function to an existing extension

Use it rather than copying a folder by hand: it generates only what was asked for, and what it generates
already passes the gate.

**Every extension written here is named below this organization's namespace**, recorded in
`package.json` under `microteia.namespace` (`microteia://workspace/info` reports it). An extension called
`billing` in namespace `com.acme` is `com.acme.billing`; `create` builds that from the short
name and refuses an id outside it. Never borrow the prefix of `examples/` — those ids belong to
whoever published them — and never invent a namespace: if `package.json` has none, ask the person
you are working for which one is theirs. An id is permanent, so a wrong one cannot be fixed later.

## Changing an extension that already exists

Every change to an extension raises its version. Two steps, in the same change, always:

1. Raise `manifest.version` in `plugin.ts` — semver: *patch* for a fix, *minor* for something new,
   *major* for anything that breaks what an earlier version wrote.
2. Add an entry at the top of that extension's `VERSIONS.md`:

       #### [1.2.0] — YYYY-MM-DD

       - What a person will notice, in one plain sentence.

The entry is written for whoever **uses** the extension, not for whoever wrote it: the change they
will see, never the file, the field or the function you touched. It is not the commit message, and it
is never the same text as one.

Do this without being asked — it is part of the change, not a follow-up. The only exception is being
told not to: if the person you are working for says to leave the version alone, leave it alone.

The version is how an installed extension recognises an update. An extension changed without a new
version is an extension that never reaches the organizations that already have it.

## Tests

Write them whenever the thing can be tested — which is nearly always, because the source is TypeScript
and the built package can be validated in a second:

    npm test                    # vitest, over every <folder>/*.test.ts

`create` already generates `<folder>/plugin.test.ts`, which validates the *built* package with the
platform's own validation. Extend it as the extension grows: a test per screen field that must stay
translatable, per message key a view reads, per rule a function enforces. Pure logic you write for a
view or a Cloud Function belongs in its own test.

A test exists so the next change fails **here**, in a second, instead of in someone's organization.
That is the whole reason this directory is TypeScript and not hand-written JSON.

## Text

Every label a person reads is a **message reference**, never a literal:

    label: '@com.example.hello/field.title'      // right
    label: 'Title'                                // wrong

The references resolve against the bundles the extension declares in `manifest.contributes`, via
`messageBundleContribution`. Ship `en` always; add other locales as extra bundles. The platform does
not translate an extension's vocabulary — the extension that declares a word answers for it.

What the organization *typed* (a screen name, a field label they created) is data, not product text,
and is never translated.

## Code

A view or `startup` may import **only** from the curated API:

- `react`
- `react/jsx-runtime`
- `react/jsx-dev-runtime`
- `styled-components`
- `@microteia/ui`
- `@microteia/data`
- `@microteia/format`
- `@microteia/i18n`
- `@microteia/theme`
- `@microteia/report`
- `@microteia/settings`
- `@microteia/functions`
- `@microteia/portal`

Any other import throws at runtime. Ask the MCP server (`describe_host_module`) rather than guessing
what a module exports.

Write views as real `.tsx` files and point at them with `sourceFile`. Never paste code into a string:
a string is not type-checked, and that is where mistakes hide.

**A view is not a page until a contribution points at it.** `views` is a registry keyed by
`views[].key`; the screen only exists once `manifest.contributes` names that key:

    nav({ key: 'summary', label: label('nav.summary'), icon: 'lineChart', order: 50 }),
    page({ key: 'summary', title: label('page.summary'), icon: 'lineChart' }, 'summary'),
    //                                                                     ^ views[].key

Forgetting the `page` is the most common mistake there is, and nothing fails: the package validates,
the extension installs, and the screen is simply not there. Same wiring for
`surfaceTab`/`surfaceWidget`, and `recordAction`/`command` for a gesture rather than a screen.

`sourceFile` also takes a **list**, merged in the order given, so a view can be written the way the
platform writes its own — the component, the state and the styles in separate files:

    sourceFile: ['./views/Panel.view.tsx', './views/Panel.viewmodel.tsx', './views/Panel.styles.tsx']

Import across those files normally: the relative import is what makes `tsc` and your editor connect
them, and the compiler removes it once they are one module. That module has **one scope**, so every
top-level name has to be unique across the list, and exactly one file exports `default`. Anything
else is refused at build time, not on the screen. `startupFile` takes a list for the same reason.

Once code is what is left, write it the way the platform writes its own, and keep the three jobs apart:
the `.view.tsx` renders and keeps no state; the `.viewmodel.tsx` keeps the state, the effects and the
handlers and returns one plain object, with no JSX; the `.styles.tsx` keeps the styled-components, and
colour in them comes from a theme token and never from a hex or an `rgba(...)`, which stop matching the
day the organization changes theme, and spacing, type and radius come from a token whenever a token means
the same thing. One file is fine while the view only renders what a hook returned; split it the first
time it keeps state of its own or derives a value.

Whatever can be **wrong** — a sort order, a total, a window of dates, which records count — goes in a
file of its own in the list, importing nothing, with a test beside it. A Cloud Function divides the same
way: the handler refuses the unauthenticated call and shapes the answer, and the decision it exists to
make sits in a plain function `npm test` can call. Logic reachable only by rendering a component or by
deploying a function is logic first tried in someone's organization. `AUTHORING.md` §7 has the shapes.

**Code does not run until a human trusts it.** A package carrying `views` or `startup` installs
inert; an administrator opens the source, reads it and trusts it, and the trust is bound to that exact
code by hash. Changing one character un-trusts it. This is deliberate — do not look for a way around it.

## Before you write

Ask the MCP server. It answers from this installation, not from a snapshot of documentation. It has
three surfaces: a **tool** takes an argument or changes something; a **resource** is a document you
attach and read; a **prompt** is a named gesture you choose. Everything that was a parameterless listing is a
resource now — a tool costs an input schema in the context window of every agent, in every session,
including the one that opened the editor only to validate a package.

**Tools — eight, and every one of them takes an argument or does something:**

- `validate_domain_model` — the gate: the domain model, checked deterministically, before anything is
  generated. An ERROR here stops the work
- `generate_artifact_plan` — what must exist, reconciled against what is already here
- `validate_plugin` — after every edit; this is the short feedback loop. It also confers every
  reference to ANOTHER extension against what its owner exports, which is the half that used to be
  checked only in the organization that installs the package
- `build_plugin` — the `.json`, without writing it
- `describe_workflow_step` — one step's exact inputs, which mapping kinds each accepts, and the
  outputs a later step can read. It also names the type a composite input needs, which is NOT the
  `…Spec` its name suggests: `upsert` takes `UpsertStepConfig`, not `UpsertSpec`
- `describe_sdk_type` — the exact declaration of any authoring type (`TemplateField`, `WidgetSpec`,
  `WorkflowStep`, `PluginManifest`…). The SDK ships its types with the comments stripped, so this is
  how you learn what a package may contain without guessing
- `describe_host_module` — what a curated module actually exports
- `describe_extension` — what ONE extension declares, brings and requires, read from the compiled
  package: the points it contributes to, the points it declares for others, its screens and their
  collections, its lists, flows, actions, scripts, views, `startup`, migrations, what it exports and
  what it demands of the Firebase project. **This is how you answer "how is X done?"** — ask it about
  the example that does X instead of reading five hundred lines and inferring
- `read_authoring_guide` — this manual, whole or by section

**Resources — read them, they cost you nothing to have open:**

- `microteia://entities` — the entities this workspace knows. **The first thing to read in any
  modelling task.** With `installed-catalog.json` present it also knows what the organization runs,
  and it always says which entity came from where and how old the snapshot is
- `microteia://domain-model/schema` — the shape a domain model must have
- `microteia://domain-model/rules` — every check, how each relationship storage is really stored, and
  the rules that decide what each SCREEN looks like
- `microteia://domain-model/coverage` — what the model canNOT say: the mechanisms this platform has
  and the vocabulary does not reach, with what each one costs. Read it when a rule seems to need
  something the model will not express
- `microteia://workflow/steps` — the step catalog. **Read it before writing any automation:** a
  `stepDefinitionId` is the one thing a declaration cannot invent, and an id that is not in the
  catalog does not run
- `microteia://workflow/events` — the trigger names a workflow may declare, and what `event.` carries
- `microteia://extension-points` — every point, its API version, and which impl kinds it accepts
- `microteia://record-commands` — the record gestures an action may run through `command`
- `microteia://expression-functions` — the functions a declarative expression may call here
- `microteia://referenceable` — every artifact another extension exports that you may point a step at,
  already in the form the reference takes. Two sources: the `plugin.ts` files here (the sibling being
  authored beside yours, which no snapshot can know about) and the extensions in the installation
  snapshot. **Read it before writing a qualified reference** — a name you cannot see is a name you
  cannot write
- `microteia://nav-groups` — every sidebar group this directory can see, BY KEY, with its name in each
  language and who declares it. **Read it before declaring a `navGroup()`**: a group is joined by key,
  never by name, and a new key with an existing name draws the same title twice in the menu
- `microteia://examples` — the first-party extensions that travel in `examples/` as source, and which
  MECHANISM each one is the best one to read for. **Read it before writing a mechanism for the first
  time**, and before deciding which folder to open; `describe_extension` answers the next question
- `microteia://example-coverage` — every mechanism this platform has, against those examples: which
  ones an example shows, which have none, and which no example COULD show because they are out of
  reach for an extension. **Read it before concluding that something cannot be done here** — the answer
  is usually an example you have not opened, or the other road this report names
- `microteia://workspace/plugins` — the extensions authored here, with their current problems and what
  each one declares in `exports`. What sits in `examples/` is ours and is named apart there: nobody
  in this organization wrote it, and nothing here installs it
- `microteia://workspace/info` — what this workspace is bound to

**Prompt — one, and it is the step that gets skipped:**

- `model_business_rule` — a business rule arrived (three lines from a conversation, not a model). It
  conducts the order: understand, model, validate, plan. Choose it BEFORE writing anything, because the
  fastest thing to do with three lines is write a screen, and that reading installs, runs, and costs
  forever

Two habits worth keeping: ask `describe_sdk_type` before inventing a property name, and read
`examples/` before writing a mechanism for the first time — those are the same sources that produce
the packages the platform itself installs, so nothing in them is a simplification.

**Automation is the part where guessing costs most**, because a wrong step id, a wrong input name or a
wrong composite shape used to install cleanly and simply not run. Two things fixed that, and both are
worth using: `check` now refuses all three, and `examples/automation-example/` is a complete,
validating automation — a workflow on save, a branch, a query, an idempotent write, a called flow with
parameters, and an action that asks a person for a value.

## Limits worth knowing before designing

- A package must stay under **800 KiB** (it is stored as one document). A warning starts at 400 KiB.
- Every reference out of the package must be **in** the package or covered by a declared
  `dependency`. `check` refuses a dangling one — and, for a qualified reference, it also refuses one
  whose owner does not declare that id in `exports`, or whose installed version falls outside your
  range. What it cannot see from here it says it cannot see, rather than refusing.
- Changing the **shape of data already written** by an earlier version of your extension requires a
  `migration` — see the guide.
